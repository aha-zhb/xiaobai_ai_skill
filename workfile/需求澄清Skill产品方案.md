# 小白用户需求澄清 Skill 产品方案

版本：V1.1  
日期：2026年10月14日  
产品工作名称：需求表达助手  
建议 Skill 名称：`clarify-intent`  
适用阶段：产品设计与后续 Skill 实现

阅读导航：第1至4章说明产品定位和用户体验，第5至10章定义核心澄清机制，第11至13章说明场景适配、案例与实现，第14至18章规定验证、风险和迭代安排。附录提供输出约定和复核清单。

## 1 产品结论与设计主张

我们要做一个面向 AI 使用小白的需求澄清 Skill。用户可以从一句不完整的话、几条零散消息或一份现有材料开始，Skill 根据这些线索提出暂时的理解，通过容易回答的选择题、具体例子和短小样例，帮助用户逐步表达自己的真实诉求，最终形成一份可以直接交给 Agent 使用的任务说明。

产品聚焦于一个目标：**Agent 承担一部分需求澄清工作，帮助用户把模糊诉求逐步变成明确任务。**

用户不需要先学习提示词，不需要填写完整需求表，也不需要解释技术实现方式。Skill 要把抽象分析留给自己，把具体判断交给用户。用户主要通过“这个更接近”“这部分不对”“两项都有”“我还没想好”来参与。

通用性来自一套稳定的判断机制：识别已有信息，找到会改变后续做法的分歧，选择当前最值得澄清的问题，生成有依据的选项，依据回答更新理解，并在足够明确时收敛。具体问题随任务变化，不采用每次都问完的固定问卷。

第一版应实现一个边界明确、可验证的 Skill，不扩展成综合 AI 培训、行业咨询、完整项目规划或任务执行系统。产品价值应通过“是否忠实表达用户意图、是否减轻表达负担、是否形成可用任务”来检验，不能只看问题数量、用户确认率或生成文字的完整程度。

本方案中的交互数量、评估阈值和发布条件属于设计建议，尚未经过真实用户验证。后续应依据实际试用结果调整，不能将其当作已证明的产品效果。

## 2 问题定义与用户理解

### 2.1 产品要解决的具体困难

用户可能熟悉自己的工作或生活情境，也能辨认结果是否合意，却不擅长提前表达背景、目标、重点和限制。他们向 Agent 提出的初始要求，常停留在“帮我弄一下”“做得专业点”“我想改善一下”“这些东西太乱了”等层面。

这些表达通常包含真实线索，但不足以唯一确定任务。Agent 如果直接执行，就需要自行补全用途、重点和结果形式；如果一次追问大量抽象问题，又把整理需求的负担交还给了用户。

本产品服务于这种表达困难，不将其归因于某个学历、专业或人群的固有能力。是否需要该 Skill，应根据当前任务是否存在表达障碍来判断。

### 2.2 用户知道什么与尚未决定什么

“心里知道自己想要什么”需要拆成两种情况。

第一种是意图已经存在，但没有表达出来。例如，用户希望领导帮助解决跨部门协调问题，却只说“帮我整理项目情况”。Skill 要从线索中提出可能的用途，让用户辨认和纠正。

第二种是用户知道自己不满意的现状，但还没有决定具体结果。例如，用户想让团队工作更有条理，却没有决定先做进度表、分工清单还是管理制度。Skill 可以帮助比较这些方向，但要保留“尚未决定”的状态，不能声称已经找到了用户隐藏的唯一答案。

两种情况可以同时出现。产品应支持意图表达与必要的局部选择，但不自行扩大为完整的业务方案设计。

### 2.3 第一版目标用户

- 能用日常语言描述部分情况，但难以写出完整任务的人。
- 有现成材料，却说不清希望 AI 如何处理的人。
- 能看出例子好坏，但面对空白页面难以从零组织表达的人。
- 不熟悉 Agent 工作方式，希望用少量对话明确需求的人。

已能清楚提出任务的用户，也可能偶尔使用该 Skill。此时产品应直接复述和收敛，避免因为启动了 Skill 就强行增加提问。

### 2.4 典型进入方式

| 初始输入 | 常见不确定性 | 首先应关注的方向 |
| --- | --- | --- |
| “帮我整理一下这些材料” | 整理的用途和重点 | 结果要帮助谁做什么 |
| “这段话写得专业一点” | 用户对专业的理解 | 具体表达效果与保留的立场 |
| “我想做个自动化” | 想减少哪一段重复劳动 | 现有操作与期望变化 |
| “帮我看看这个表” | 想发现问题还是形成结论 | 用户要做出的判断 |
| “这个我不太满意” | 不满意的具体部分 | 对比、小样或具体反例 |
| 只上传材料，没有任务说明 | 材料与诉求的关系 | 是否需要处理及处理用途 |

上述进入方式只是识别线索，不是关键词触发清单。表达简单不等于需求模糊，材料复杂也不等于必须进行长时间澄清。

## 3 产品目标与范围

### 3.1 用户完成后的变化

用户应能看到一份自己认可的任务说明，知道其中哪些是已确认要求、哪些是暂定安排、哪些问题仍需保留。用户可以直接复制这份说明，或者让当前 Agent 在已有授权范围内接着处理。

对于局部澄清任务，产品只补清当前缺失的部分，不必把整个对话重新整理成完整规格书。

### 3.2 产品承担的工作

1. 阅读用户提供的话语和已可访问材料，提取与需求有关的线索。
2. 区分用户明确表达、材料记载、AI 推测和未决事项。
3. 识别可能导致不同执行方向的理解分歧。
4. 用具体、短小、可否定的问题帮助用户判断。
5. 必要时通过例子、对比、局部小样降低回答难度。
6. 根据新回答修正理解，保留重要要求与未决事项。
7. 生成用户容易核对、后续 Agent 能使用的任务说明。

### 3.3 第一版范围边界

| 事项 | 第一版处理方式 |
| --- | --- |
| 澄清真实用途、目标、重点和边界 | 核心能力 |
| 提供短例子帮助判断风格或形式 | 澄清手段 |
| 提出容易修改的暂定安排 | 明示后可采用，不写成用户已确认要求 |
| 输出完整文档、程序或业务方案 | 归后续执行任务，不由澄清阶段自动展开 |
| 修改文件、发送消息、发布内容 | 依据原始或后续指令中的实际授权和权限边界处理，不把意图选择视为新增授权 |
| 讲解 AI 原理、教授提示词 | 用户明确提出时再处理，不作为必经过程 |
| 查询外部事实或开展专业诊断 | 在任务范围与工具能力内按需处理，不为猜测需求自动扩展 |
| 决定用户立场、预算、对外承诺 | 必须保留给用户，不能用默认值替代 |
| 跨会话保存用户偏好 | 第一版不依赖该能力，遵守宿主的实际机制 |

### 3.4 必须守住的产品原则

**忠实于意图。** AI 提出的候选方向是帮助识别的工具，用户可以否定全部方向。产品不能把顺着选项选择解释为全面接受 AI 的方案。

**问题有作用。** 每次提问都应能说明它解决什么分歧，以及答案如何影响下一步。仅用于填满字段的问题应删去。

**负担可感知。** 用户应知道当前正在确认哪一件事，不需要理解需求分析术语或内部状态。

**不确定性可保留。** 尚未决定不是错误。对当前任务不构成障碍的未知可以留待后续处理。

**修正真实生效。** 用户纠正后，旧理解应从当前任务说明中退出，不能一边承认纠正，一边继续沿用原来的假设。

## 4 产品交付与交互体验

### 4.1 用户看到的最小体验

用户输入一句话或材料。存在关键不确定性时，Skill 显示一句简短、带保留的理解，再提出一个具体问题。用户选择或纠正后，Skill 继续处理关键分歧；信息足够时，直接给出一份简短任务说明供核对。

默认一轮围绕一个主要问题，提供两至三个核心选项。两个问题只有在相互独立、都容易回答时才合并。数量是体验默认值，不能用来限制必要的澄清，也不能被理解为必须问够。

基本表达示例：

> 你提到想把项目情况整理清楚，我暂时理解为要方便后面使用。你现在最想用它做什么？
>
> A．给领导汇报，让他了解情况、帮助协调。  
> B．自己掌握进度，找出遗漏或延期。  
> C．安排团队下一步工作。  
>
> 如果都不接近，也可以直接说你最想解决的事。

这不是固定话术。已有充分线索时，直接围绕更具体的分歧提问；不需要每轮重复“我暂时理解”。

### 4.2 用户可使用的回答方式

用户可以回复选项字母、完整句子、多个选项、部分认同或新的材料。Skill 应理解这些回答的含义，不要求用户遵守输入格式。

“A，但不用给领导看”应被识别为对用途的修正，而不能只提取字母 A。“都行”不意味着所有选项的含义同时成立。“第二种更像，但我主要是想……”中的补充描述优先于机械编号。

### 4.3 任务说明的两层表达

第一层是给用户看的自然语言说明，使用用户熟悉的词，保留用途、重点和重要边界。

第二层是必要的补充信息，包括暂定安排、关键未决事项和相关材料位置。简单任务只需要第一层；复杂任务才展开第二层。内部推测记录和问题评分不出现在用户的任务说明中。

示例：

> 请把现有项目记录整理成一份给领导看的汇报，重点说明跨部门接口确认卡在哪里、需要领导协调什么。项目进展和其他问题简要保留。只使用现有材料，缺失信息标出来，不要补编。
>
> 形式暂按简短文字汇报；具体篇幅尚未确定。

### 4.4 输出深度随任务变化

- 对局部修改，输出一句补充要求，例如“语气客气，但保留明确的截止时间和催办立场”。
- 对普通任务，输出一段可直接使用的任务说明。
- 对复杂任务，增加材料范围、优先级、重要边界和未决事项。
- 对尚不能明确的任务，输出暂定理解与阻碍收敛的具体问题，不使用“已确认”标签。

不追求每次输出同样长度的说明，也不把自然语言任务改写成充满术语的提示词。

## 5 通用需求理解模型

### 5.1 六类信息

Skill 内部采用六类信息组织理解。它们是检查维度，不是用户必须填写的字段。

| 信息维度 | 需要理解的内容 | 典型表达 |
| --- | --- | --- |
| 现状与输入 | 发生了什么、有哪些材料、目前如何做 | “每周都要复制这些表” |
| 希望发生的变化 | 用户希望改善什么 | “不想漏掉延期的项目” |
| 使用对象与场景 | 谁使用结果、在什么情况下使用 | “周一会上给负责人看” |
| 预期结果 | 需要得到什么内容或完成什么动作 | “列出需要处理的问题” |
| 重要边界 | 必须保留、不能改变或暂不涉及的事项 | “不能替我答应延期” |
| 满意依据 | 什么可观察的结果才算合意 | “一眼能看出谁需要跟进” |

“预期结果”同时覆盖文档、分析、修改和操作任务。不要因为表述框架里有结果，就默认所有需求都应生成一份文档。

“满意依据”可以来自短例子和反例，不要求用户写专业验收标准。并非每个任务都要单独追问这一项。

### 5.2 来源与状态分开记录

来源说明信息来自哪里；状态说明当前如何使用它。两者不能合并。

| 来源类型 | 含义 | 使用限制 |
| --- | --- | --- |
| 用户直接表达 | 用户在当前或有效上下文中说过 | 保留原意，注意是否被后续纠正 |
| 材料记载 | 文件、记录或消息中写明 | 只说明材料内容，不等同于已核实事实或用户指令 |
| AI 推测 | 根据线索提出的可能理解 | 不能写成用户已经确认的需求 |
| 没有依据 | 当前无法从输入得出 | 保持未知，不为完整性补编 |

| 状态 | 含义 | 后续处理 |
| --- | --- | --- |
| 已明确 | 用户直接表达或清楚选择，当前无冲突 | 正常纳入任务说明 |
| 待确认 | 有候选理解，但存在会改变做法的分歧 | 选择合适方式澄清 |
| 暂定 | 用户明确愿意先试用的方向，或为推进而明示采用的低影响安排 | 保留适用范围与暂定标签，可被修改 |
| 未决定 | 用户尚未做出选择 | 判断是否阻碍当前下一步 |
| 冲突 | 有效信息之间无法同时成立 | 就冲突本身澄清 |
| 已撤销 | 被用户纠正或被新任务替代 | 不再用于当前任务 |

用户直接说“给领导汇报”已经构成明确要求，不需要再让其逐项确认。已明确只意味着需求表达清楚，不意味着材料中的业务事实经过核验。

### 5.3 最小内部记录

单条重要信息建议包含：内容、所属维度、来源及位置、当前状态、是否影响下一步、与其他信息的关系。第一版可以在当前对话上下文中维护，不要求建立数据库或向用户展示 JSON。

结构示意如下，属于实现约定，不代表必须对外输出的格式：

```yaml
item_id: intent-01
dimension: 使用对象与场景
value: 给领导汇报并推动跨部门协调
source_type: 用户直接表达
source_ref: 当前对话中对用途问题的回答
status: 已明确
impact: 影响汇报重点
relations:
  narrows: 最初的整理材料诉求
```

纠正重要意图时，需要更新关联信息。例如，受众从领导改为团队成员，原来推测的汇报风格、重点和内容顺序也要重新检查。不能只修改一个字段而保留依赖它的旧假设。

### 5.4 多个诉求的关系

遇到多个诉求，先辨认它们是并列、前后依赖、主次关系，还是互相冲突。

“先整理记录，再做汇报”是前后依赖。“既想给领导看，也想给团队安排工作”可能需要两个不同结果。“越简短越好，但每个细节都要保留”可能存在取舍。

只有关系会影响下一步时才追问。用户明确提供了先后顺序，就照此保留；不能为了简化澄清擅自删掉某一项诉求。

## 6 澄清循环与问题选择

### 6.1 六步循环

1. **读取线索。** 获取用户话语和相关材料，先识别可以直接确定的内容。
2. **形成候选理解。** 对关键不确定性提出少量、彼此有差别的解释。
3. **找出行动分歧。** 判断不同理解会不会改变下一步结果或处理方式。
4. **选择澄清动作。** 在提问、实例回忆、对比、小样和直接收敛之间选择。
5. **更新任务理解。** 根据用户回答确认、补充、撤销或保留信息。
6. **判断是否足够明确。** 达到条件就生成任务说明，否则进入下一轮。

每次新输入都会重新触发判断，不使用不可变的题目顺序。流程中的“动作”不一定是问题：已足够明确时，正确动作就是收敛。

### 6.2 候选理解的形成

候选理解应主要来自用户用词、材料内容、前文用途和现有任务关系。当线索不足时，可以使用少量日常用途作为探索，但要明确其暂时性。

一个候选理解需要回答：它为什么合理，与其他候选差别在哪里，用户如何否定它。没有具体差别的候选应合并；需要大量额外事实才能成立的候选不应优先展示。

例如，从“项目记录”提出汇报、跟踪和安排工作的用途具有解释力；直接提出建设企业级平台，就超出了现有线索。

### 6.3 判断一个问题是否值得问

先写出问题对应的分歧，再比较不同答案带来的后续做法。如果无法说明行动如何改变，暂不问该问题。

问题优先级采用定性判断，避免在第一版引入没有依据的精确权重。

| 判断因素 | 优先澄清的情况 | 可延后或省略的情况 |
| --- | --- | --- |
| 对行动的影响 | 会改变用途、重点、立场或结果种类 | 只改变易修改的呈现细节 |
| 现有信息的充分程度 | 有多个合理解释，材料不足以区分 | 用户已经明确说过 |
| 用户的回答难度 | 可用日常场景或具体例子回答 | 需要用户先学术语或做大量分析 |
| 误解后的修改成本 | 方向错误会导致大量返工 | 以后可以轻松调整 |
| 当前任务的推进需求 | 不明确就无法确定下一步 | 与当前下一步无关 |

多个问题都重要时，优先问影响范围更大、容易回答的那个。某个问题影响大但用户难以回答时，先换成具体实例或小样，不能因为难问就悄悄替用户决定。

### 6.4 防止材料本身决定用途

材料形式只提供线索。上传表格不代表要做图表，上传文档不代表要总结，提供会议记录不代表要生成纪要。

如果用户已经说“按这份会议记录写纪要”，用途与结果形式已明确。此时重点可能是保留程度、行动事项或某个冲突，不再询问是否要总结。

### 6.5 局部问题优先于完整扫描

用户已经开展任务，后来表示“这部分不对”时，先定位不满意的部分。不要重新启动全量澄清，也不要要求重述已经明确的背景。

用户补充材料时，先判断新材料改变了哪些理解。与当前分歧无关的材料不应导致无意义的新问题。

## 7 问题与选项的设计规范

### 7.1 单个问题的结构

一个有效问题通常包含：必要的上下文、一件需要判断的事、容易比较的选项，以及可以纠正理解的入口。

上下文只保留让用户看懂问题的内容，通常一句即可。不要先输出长篇分析再问一个问题，也不要暴露内部推理过程。

不适合的表达：

> 请明确需求目标、受众画像、交付颗粒度、约束条件与验收指标。

更适合的表达：

> 你希望对方看完后，主要了解事情的进展，还是帮你推动解决一个问题？

### 7.2 选项的七项质量要求

1. **同一维度。** 一组选项回答同一件事，不能把用途、格式和风格混在一起。
2. **具体可辨。** 用户能想象选中后会得到怎样的结果，或下一步会怎样不同。
3. **线索相关。** 优先围绕现有输入生成，不堆砌与当前任务无关的方向。
4. **表达平衡。** 长度、语气和完整程度尽量相近，避免某项明显更高级或更诱人。
5. **确认粒度适当。** 一个选项不能打包多个独立决定，让用户误选一部分却被视为全选。
6. **可被否定。** 用户可以纠正全部选项，而不被迫选择最接近的一项。
7. **关系明确。** 真正互斥的选项按单选呈现，可兼容的选项允许组合，涉及主次时说明在问哪个最重要。

核心选项默认两至三个。取消理解、暂时不知道和自由补充是退出或修正方式，不需要与每个核心选项同样展开。

### 7.3 不能打包的确认

不适合的选项：

> A．给领导做一份正式十页 PPT，使用政策语言，并提出预算申请。

这同时包含受众、形式、篇幅、风格和业务行动。用户可能只认可“给领导看”，其他要求都是 AI 添加的。

更合适的选项：

> A．给领导汇报进展和需要协调的问题。

用户选择后，只把受众和主要用途纳入已明确需求。只有当形式、篇幅或预算申请会改变当前做法时，才继续澄清这些事项。

### 7.4 不确定事项不默认推荐

真实意图缺乏依据时，不将某一项标为推荐。用户往往希望获得帮助，产品需要防止“推荐”替代其自己的判断。

有明确约束支持的建议可以说明理由，例如“你说只有三分钟发言，我建议先保留两个关键问题”。这属于基于条件提出的安排，不等于已经获得用户对其他含义的确认。

### 7.5 确认范围与开放回答

用户选择哪一项，就确认该项清楚表达的含义。没有写在选项里的要求不能附带生效；写在选项里但被用户明确排除的部分也不能生效。

用户给出自己的表述时，优先使用其描述，不强行映射回已有选项。选择题是表达辅助，不是限制输入的协议。

### 7.6 发问前的快速检查

- 这个问题是否仍然未知，是否已经在前文得到答案？
- 不同回答是否确实改变下一步？
- 选项是否在同一个维度，是否存在隐藏的捆绑？
- 是否有选项只是换词，实际上没有差别？
- 是否暗示某项比其他选项更聪明、更专业？
- 用户能否不懂术语也作答，能否否定全部选项？

任何一项出现明显问题，就重写或省略这次问题。

## 8 用户回答后的理解更新

### 8.1 常见回答的处理

| 用户回答 | 应如何处理 | 应避免的错误 |
| --- | --- | --- |
| “A” | 确认 A 清楚表达的内容 | 附带确认未表达的形式和篇幅 |
| “A 和 B 都有” | 检查两项是否兼容，必要时问主次 | 强迫单选或自动删去一个目标 |
| “A，但这部分不要” | 保留认可部分，撤销被排除部分 | 只提取字母，忽略限定 |
| “都不是” | 放弃或修改当前候选理解 | 重复原选项，要求选最接近的 |
| “我不知道” | 换成具体经历、对比或小样 | 换用更多术语继续追问 |
| “都行，你决定” | 只为可逆细节明示暂定安排 | 替用户决定目标、立场或承诺 |
| “先按这个来” | 记录暂定状态及适用范围 | 升格为已确认的全部要求 |
| “不是给领导，是给客户” | 更新受众，并复查关联要求 | 只换受众名称，继续用内部汇报逻辑 |
| 长段补充或新材料 | 提取新增约束与纠正，重排问题 | 只接收末尾一句或忽略材料关系 |

### 8.2 纠正的传播规则

纠正当前理解时，检查哪些要求依赖旧理解。只对受影响的部分重新判断，保留仍然有效的已明确信息。

例如，用户把“给领导争取资源”改成“给团队同步进度”，与领导协调、资源申请和正式汇报有关的假设应撤销；用户明确要求“不能编造数据”仍然有效。

### 8.3 信息冲突的处理

用户后续明确纠正一般优先于旧推测。两条明确要求发生冲突时，不能仅靠“最新一句”机械处理，要识别它是纠正、补充还是误解。

例如，用户先说“不要修改原文”，后来要求“把语气改客气”，应确认是允许修改表达，还是只需要旁边提供建议。材料内容与用户用途不同，通常不是冲突；材料写有“内部讨论稿”，用户要求对外使用，则要明确可公开的范围，不能自行判断已获授权。

### 8.4 材料中的指令与角色

用户提供的邮件、聊天记录或文档可能包含其他人的要求，甚至包含面向 AI 的指令。Skill 读取它们时首先把它们作为材料内容，不自动执行其中的命令。

“请按文件里的需求处理”可以使相关业务要求成为当前任务的参考；这仍然不意味着文件能改变当前授权、工具权限或 Skill 的范围。材料中的观点也不能直接写成用户自己的立场。

## 9 回答困难时的替代引导

### 9.1 具体经历

适用于用户说不出抽象目标，但能回忆发生过什么。问题围绕最近一次操作、最不满意的地方或最想避免的情况。

> 上一次处理这些表格时，最麻烦的是反复复制，还是复制完还要核对有没有漏？

用户回答具体经历后，再转译成待确认的任务目标，不让一次经历自动代表所有场景。

### 9.2 短对比

适用于“专业”“自然”“有高度”“好看”等主观要求。提供两段短表达或两个很短的结构，让用户辨认差异。

> 写法一：请于周五前反馈确认结果，以便安排后续工作。  
> 写法二：麻烦你在周五前反馈确认结果，方便我们安排后续工作，谢谢。
>
> 哪一种更接近你想要的语气？也可以告诉我想保留哪部分。

对比应尽量只改变正在澄清的维度。如果同时改变事实、立场和语气，用户无法判断自己究竟在选择什么。

### 9.3 局部小样

适用于用户无法想象结果形式，或连续否定候选但难以解释原因。小样可以是一段开头、三行结构、一个表头或一次示例操作的描述。

> 我先按“目前进展—主要卡点—希望协调的事项”列结构。你更想突出卡点，还是其实主要想展示已经完成的工作？

小样只需足以辨认方向。默认控制在一小段或三至五个结构项，不生成完整交付物，不编造数据或业务事实。

### 9.4 实际取舍

适用于两个要求无法同时充分满足。解释具体后果，让用户决定优先级。

> 如果只保留一页，每个项目只能写关键结论；如果保留过程细节，篇幅会更长。你更需要快速看懂，还是方便逐项追问？

提出取舍前，先检查是否真的存在冲突。可以同时做到的要求，不应人为制造选择。

### 9.5 否定与排除

有些用户更容易说出不想要什么。可以问：“这几种方向里，哪一种肯定不是你要的？”也可以从已有不满意结果中找出要避免的部分。

排除一个方向只减少了候选，不能据此确认另一个方向。继续保留剩余不确定性。

### 9.6 连续无进展

连续两次无法缩小关键分歧时，建议改变方式，避免在同一维度改写选项后继续追问。可以使用一个具体事件、小样，或复述当前已知内容并说明只差哪件事。

“两次”是切换方式的默认提醒，不是最大澄清轮数。若用户愿意继续且确有新信息，可以继续。若缺少决定方向所必需的事实，则明确缺口并保留任务状态，不能为了结束对话假装需求已明确。

## 10 收敛与停止条件

### 10.1 足够明确的判断

同时满足以下条件，可以生成任务说明：

1. 能明确表达当前要完成的动作或结果，以及用途或期望变化；只对当前任务确有必要的维度作要求。
2. 已处理会使下一步朝明显不同方向发展的关键分歧。
3. 已明确的重要边界可以在说明中保留，剩余未知可以标出或暂定。
4. 能形成用户容易核对的具体表达，不依赖大量未确认的推测。

复杂长期目标可以先收敛到一个已获用户认可的下一步，不必把整个项目设计完。但这个下一步应与原诉求的关系清楚，不能被伪装成全部需求已经解决。

### 10.2 四种结束状态

| 结束状态 | 条件 | 对用户的表达 |
| --- | --- | --- |
| 已明确 | 核心要求清楚，关键分歧已处理 | 给出任务说明，方便局部纠正 |
| 暂定可用 | 用户愿意采用明示假设，下一步范围受限 | 给出暂定任务与重要假设 |
| 需要补充 | 缺少会改变方向的事实或业务决定 | 说明已知内容和一个具体缺口 |
| 用户停止或转向 | 用户取消、暂停或提出新的目标 | 保留有效信息，按新指令处理 |

只有“已明确”可以把整项任务标为已明确或已确认。其他结束状态仍可标出其中已经明确的局部要求。“暂定可用”不能在交接后丢失假设。“需要补充”也可以是合格结果，前提是缺口真实、具体，且已经降低了用户的表达负担。

### 10.3 暂定安排的适用边界

可暂定的常见事项包括简短文字说明、普通标题、初步内容顺序等容易调整的呈现细节。前提是没有与已知要求冲突，并且清楚写明。

用途、核心目标、数据事实、业务立场、预算和对外承诺不能因为用户未回答而默认。涉及文件范围和外部动作的权限，也不能通过选项默认获得。

用户明确说“先按这个方向试”时，可以将所指方向记录为用户选择的暂定目标。它与 AI 因用户未回答而默认目标不同，必须保留用户选择的范围，不能顺带添加其他业务决定。

### 10.4 最后确认的方式

最后复述应突出最重要的用途、重点和边界。用户已经清楚表达的要求不必逐项重复审批。

> 我理解，你主要想让领导推动跨部门接口确认，所以汇报重点放在卡点和需要协调的事项，已完成工作简要保留。下面这段是否准确？不准确的地方可以直接改。

已经得到清楚选择且没有新增核心推测时，可以直接交付说明，不强制再等一句“确认”。仍存在重要推测时，将其标为待确认，不自行升级为确定要求。

## 11 场景适配与通用性边界

### 11.1 通用机制与局部表达

通用机制负责判断信息是否充分、哪个分歧重要、怎样提问和何时停止。场景适配只改变问题中的词、例子以及当前需要关注的维度。

第一版不建立庞大的行业问卷库。可以维护少量场景示例，帮助模型理解如何将抽象维度改写成用户熟悉的语言。示例不能成为强制流程。

| 场景 | 可能值得澄清的分歧 | 适合的引导方式 |
| --- | --- | --- |
| 写作与沟通 | 想让对方了解、同意、回应还是采取行动 | 用途选择、短语气对比 |
| 材料整理 | 保留原貌、快速查找、汇报重点或安排行动 | 用途选择、短结构小样 |
| 表格分析 | 找异常、比较变化、核对问题或支持决策 | “看完要决定什么”的具体选择 |
| 重复操作 | 想减少哪段操作、哪些判断必须保留 | 最近一次操作、输入输出对照 |
| 学习与理解 | 希望知道大意、掌握做法还是解决一道题 | 当前卡点、讲解小样 |
| 视觉与呈现 | 不满意的是信息顺序、密度、风格还是用途匹配 | 参考对比、局部结构 |

### 11.2 专业知识不足时

Skill 可以澄清用户想解决的问题，却不应依靠自己不了解的行业细节构造看似专业的选项。

例如，用户提供陌生技术报告并说“帮我看看”，可以先确认是希望了解大意、找出疑问还是整理成可沟通的问题。不能编造专业诊断结论，再让用户在结论之间选择。

专业准确性属于后续任务的验证要求，不能由“用户选择了某一项”替代。

### 11.3 材料不可读或缺失时

明确说明已看到什么、未能读取什么。先利用用户文字开展不依赖缺失材料的澄清；需要材料内容才能继续时，指出具体缺口。

不能假装已经读过附件，也不能让用户重述全部背景。可以请求一段相关内容或一个具体例子，减少补充负担。

## 12 完整交互案例

以下案例用于说明期望行为，不代表已经完成的产品测试。案例中的材料条件均在案例内给出，不能迁移为其他用户的事实。

### 12.1 项目记录整理为领导汇报

**初始输入**

用户提供几条项目记录，其中包括已完成的事项、人员未到位和接口确认无人牵头，并说：“最近事情太乱了，帮我弄一下。”

**第一轮**

> 这些记录既可以用于掌握进度，也可以整理成汇报。你现在主要想用它做什么？
>
> A．给领导汇报，让他了解情况、帮助协调。  
> B．自己掌握进度，找出遗漏或延期。  
> C．安排团队下一步工作。

用户：“A，主要是希望领导帮忙推动。”

**理解更新**

已明确：受众是领导，主要用途是推动解决问题。未知：最希望推动哪类问题。尚未确认 PPT、篇幅或预算申请。

**第二轮**

> 记录里有人员安排和跨部门接口确认两类卡点。这次最希望领导先推动哪一类？
>
> A．人员安排。  
> B．跨部门接口确认。  
> C．两类都需要推动。

用户：“B，人员问题先简单带一下。”

**输出任务说明**

> 请把现有项目记录整理成一份给领导看的汇报，重点说明跨部门接口确认卡在哪里，以及需要领导推动的事项。项目进展和人员问题简要保留。只使用材料中已有的信息，缺失事项标出来，不要补编。形式暂按简短文字汇报。

**验收关注**

用户选择只确认其表达的用途和重点；人员问题仍然保留；文字形式清楚标为暂定；没有为了补全格式而继续追问。

### 12.2 用户否定全部选项

**初始输入**

用户上传会议记录：“帮我处理一下这个。”

Skill 提出写纪要、提取待办、整理给领导看的摘要。用户回答：“都不是。我只想知道会上大家到底有没有答应我的事情。”

**正确更新**

撤销原来的结果方向，明确用户关注的是承诺和回应。可以围绕“只找明确承诺，还是也标出含糊回应”提出一个相关问题。

**输出方向**

> 请根据会议记录，找出与我提出事项相关的回应，区分明确答应、附条件答应和未明确表态。引用对应原话，不把讨论建议写成承诺。

**验收关注**

重新理解需求，而不是要求用户从原来的三项里选一个；没有将“提到过”解释为“答应了”。若用户提出事项在记录中无法识别，应先确认对应事项。

### 12.3 主观语气通过短对比澄清

**初始输入**

用户提供一封催办邮件，原文包含本周五截止时间、待反馈事项和对应责任人，并说：“写得客气一点，但别显得我很好说话。”

**澄清动作**

用途和保留立场已明确，提供两种短语气对比，不再问收件人是谁才能开始。若收件人关系确实影响措辞，再局部补问。

用户选择“保留截止时间，语气缓和一点”的样例。

**输出任务说明**

> 请把这封催办邮件的语气改得客气一些，保留原来的截止时间、责任要求和催办立场。避免添加让步承诺，也不要替我解释对方延期的原因。

**验收关注**

只澄清主观程度，不把“客气”改成取消截止时间。新增边界应有原文或用户表述依据；本例的避免让步来自“别显得我很好说话”的意图。

### 12.4 自动化需求从操作经历开始

**初始输入**

“我每周都要整理这些文件，想让 AI 帮我省点事，但不知道怎么说。”

**第一轮**

> 你最近一次整理时，哪段最花时间？
>
> A．给文件改名、分到不同文件夹。  
> B．把不同文件里的内容汇总到一起。  
> C．检查缺了哪些文件或信息。  
>
> 也可以直接说你当时是怎么操作的。

这些是探索方向，不能声称已从材料读到。用户回答：“B，我要把每个人发来的进度复制进同一张表，但会漏。”

**第二轮**

> 你更希望先解决哪件事？
>
> A．先把内容汇总起来，自己再核对。  
> B．汇总时同时标出缺失或无法对应的内容。

用户选 B。

**输出任务说明**

> 我希望把每个人提交的进度内容汇总到现有表格，并标出缺失或无法对应的内容，减少漏项。开始实现前，需要确定输入文件的样式、汇总表对应字段和匹配规则；这些信息目前仍待补充。

**验收关注**

先找到重复劳动与期望变化；关键输入规则保留为下一步缺口；不在需求尚未明确时选定编程语言、安装工具或运行脚本。

### 12.5 用户已经表达清楚

**初始输入**

“把这段通知压到150字以内，发给团队成员，保留周五截止时间，语气直接一点。”

**正确行为**

直接形成任务说明，或依据当前请求进入后续修改。不要再问目标、受众、篇幅、用途和语气。只有发现原文信息与明确要求冲突时才补问。

**验收关注**

Skill 被调用不意味着必须提出选择题。减少不必要的对话本身就是正确行为。

### 12.6 多目标与关键未决事项

**初始输入**

“我要给领导看，也要让同事知道怎么做，最好一页说完，而且所有细节都要有。”

**澄清动作**

先确认这次主要使用场景，或说明可以有简短主体加详细附件。方案选择只用于澄清结果组织方式，不自行决定删掉细节。

用户：“主体给领导看，同事可以看附件。”

**输出任务说明**

> 请将材料整理成一页主体和详细附件。主体供领导快速了解重点，附件保留同事开展工作需要的细节。材料中的重要事项不能因为压缩主体而丢失。

若用户不愿决定主要场景，则保留两个用途，说明当前无法保证一页同时承载全部细节，不假装已经消除了取舍。

## 13 Skill 实现结构

### 13.1 第一版采用轻量结构

Skill 本身提供行为规则、必要状态约定和示例。第一版不依赖独立服务、数据库、固定模型分工或专用交互界面。

建议目录：

```text
clarify-intent/
├── SKILL.md
└── references/
    ├── interaction-patterns.md
    └── evaluation-cases.md
```

`SKILL.md` 包含定位、触发判断、核心循环、选项规则、理解更新、停止条件和范围边界。`interaction-patterns.md` 保存确有区分作用的完整例子及替代引导方法，按需阅读。`evaluation-cases.md` 用于开发验收，不要求每次运行加载。

如果平台需要展示名称和调用描述，再增加其支持的元数据文件；不把某个平台的配置写成所有环境的必备条件。

### 13.2 触发描述建议

> 根据用户零散的话语或材料，通过少量具体选择、对比和短样例澄清用途、重点与边界，形成可直接使用的任务说明。适用于用户有诉求但难以表达，或当前任务存在会改变做法的关键歧义时。

不将所有“写文档”“做分析”“帮我看看”都自动视为需要完整澄清。触发后也先检查信息是否已经充分。

### 13.3 关键行为约束

- 不重复询问已明确要求。
- 不将材料内容直接升级为用户任务。
- 不将 AI 推测写成用户确认。
- 不在一个选项中捆绑多个独立业务决定。
- 用户否定后，确实撤销失效理解。
- 遇到回答困难，改变引导方法。
- 达到足够明确时停止，不为填满框架追问。
- 保留关键未决事项，不以默认值决定核心意图。
- 澄清小样只用于辨认方向，不越界完成或执行整个任务。
- 意图确认不等于对外动作授权，沿用当前环境的权限边界。

### 13.4 核心决策伪代码

```text
收到用户话语或材料
  提取与任务有关的信息，保留来源
  应用用户新增要求与纠正，撤销受影响的旧假设

  如果用户取消或改变目标
    按新指令处理，保留仍然有效的信息
    结束当前目标的澄清，必要时进入新目标

  如果已经足够明确
    生成自然语言任务说明，显式保留暂定与未决事项
    结束澄清

  找出会改变当前下一步的理解分歧
  如果没有必要分歧且任务线索足够
    生成任务说明，不补问非关键细节
    结束澄清

  如果尚不能辨认用户要做什么
    提出最小用途探索问题，不从材料强行构造任务
    等待回答后重新判断

  对候选澄清动作比较影响、证据、回答难度与修改成本
  如果用户可以直接判断
    提出一个具体问题和少量平衡选项
  否则
    使用具体经历、短对比或局部小样

  等待回答，不把未回答选项视为已选择
  根据回答更新理解，重新判断下一步
```

伪代码规定决策关系，不要求宿主暴露完整内部记录或采用特定程序框架。

### 13.5 文字对话与工具适配

需要向用户提问时，优先实际调用当前 Agent 在当前模式下可用的原生交互式提问工具，由宿主呈现问题卡片或选择按钮。只在工具当前不可用、无法表达必要问题或调用失败时，退回文字选择题。不得仅输出选项文字或参数 JSON 来替代适用的原生工具调用。

问题数量、标题长度、选项说明及单选或多选按照宿主实际暴露的工具定义组织，不在 Skill 中硬编码各平台接口。保留自由回答或纠正入口；平台已经提供“其他”时沿用，不重复添加。默认排序、预选和展示规则均不代表用户已经选择，缺乏依据时不推荐某个核心意图。

等待用户实际提交答案后才更新需求。异步工具显示问题或返回排队成功不等于已回答；取消、未回答及超时都不能视为确认。参数错误可依据真实定义修正一次，仍失败则退回文字。

Skill 决定问什么，Agent 根据自己的工具定义调用提问能力，界面由宿主负责。第一版不为此建设平台适配架构，也不预设所有 Agent 的当前版本必然具备同一种能力；真实卡片显示与答案回传应在宿主内另行验证。

### 13.6 跨会话交接

第一版优先支持复制任务说明。交接信息包括已明确要求、重要暂定安排、未决问题和必要材料引用，不包含冗长的内部分析。

在新会话中，后续 Agent 应能识别哪些要求来自用户、哪些属于建议。材料引用应对应真实位置；新会话无法访问原材料时，需要用户或宿主补足访问条件，不能承诺自动带入附件。

## 14 产品验收与评估设计

### 14.1 第一版需要验证的假设

| 假设 | 怎样验证 | 可能推翻假设的信号 |
| --- | --- | --- |
| 具体选择比抽象问卷更容易回答 | 同类任务比较回答困难与主观负担 | 用户需要理解大量选项才能继续 |
| 动态问题能减少无效往返 | 检查每轮解决的分歧与重复问题 | 问题少，但核心误解没有消除 |
| 短小样能帮助表达主观要求 | 比较小样前后的具体纠正信息 | 小样诱导用户接受原本不想要的方向 |
| 任务说明能保留真实意图 | 逐项对照原话、选择与纠正 | 说明流畅，却增加或遗漏关键要求 |
| 跨场景可以共用一套机制 | 在不同任务种类上评估相同行为要求 | 必须靠大量行业专用问卷才能工作 |

这些是假设，不应在产品介绍中提前写成已实现的效果。

### 14.2 评估的三个对象

**过程。** 问题是否必要，选项是否平衡，用户纠正是否生效，是否及时更换引导方法。

**结果。** 任务说明是否忠实、可用，核心要求是否保留，推测是否标明，未决事项是否准确。

**用户体验。** 用户是否容易回答，是否感觉被理解，是否能纠正结果，是否愿意用这份说明继续开展任务。

不能仅凭“用户说对”判定成功。用户可能只是接受了最省事的选项，也可能没有注意到说明中的附加要求。

### 14.3 主要指标与统计口径

| 指标 | 建议口径 | 解读注意 |
| --- | --- | --- |
| 意图保真率 | 有用户依据且符合原意的确定性关键陈述数，除以全部确定性关键陈述数 | 将暂定与未决事项单独统计，不能混作已确认 |
| 关键遗漏率 | 未被最终说明保留的关键要求数，除以有效的已明确关键要求数 | 以有效的最新要求为准，撤销要求不算遗漏 |
| 无依据确定陈述率 | 无依据的确定性关键陈述数，除以全部确定性关键陈述数 | 核心目标或立场出现一次就应重视 |
| 重复问题率 | 非必要重复问题数，除以全部澄清问题数 | 因真实冲突进行核对不算重复 |
| 有效澄清轮次 | 形成可用说明前，确实缩小重要分歧的交互次数 | 同时记录总轮次和复杂度，不能只追求少 |
| 纠正生效率 | 正确撤销旧内容并更新关联理解的纠正事件数，除以需要更新的明确纠正事件数 | 检查最终说明，不能只看回应语气 |
| 用户负担 | 用户对回答难度与必要程度的反馈，以及退出原因 | 不用响应速度直接替代心理负担 |
| 后续可用性 | 独立阅读说明的人能否指出明确的下一步及重要边界 | 允许正确识别“需要补充”，不强迫假装完整 |

只有有明确分母的案例才计算比例，分母为零时记为不适用。不同复杂度任务分别统计，并保留案例数量；第一版不输出没有校准依据的单一综合分数。

### 14.4 场景评估与真实用户评估分开

场景评估检验规则是否得到遵守。预先准备原始输入、用户后续回答和需要检查的行为，但不要求模型输出某一句标准话术。不同表达只要保留同样意图都可以合格。

真实用户评估检验用户是否能借助引导表达。不能让所有参与者照着预写答案选择，也不能只找已经熟悉提示词的人测试。

对于已有明确意图的任务，可先私下记录用户自己的用途与边界，供最终对照，避免确认过程改变了原始意图而无法察觉。对于尚未决定的任务，记录最后如何作出决定，以及用户是否理解取舍，不强行要求匹配一个预设答案。

### 14.5 对照方式

建议比较三种方式：普通自由对话、固定需求问卷、本 Skill 的动态澄清。尽量保持材料、任务复杂度和宿主能力相近，并平衡任务顺序，减少先做一次任务带来的熟悉效应。

关注结果保真、回答负担与后续可用性。若动态澄清更短但误解更多，不能认定更好；若更准确但用户明显难以作答，也需要调整选项和引导方式。

### 14.6 建议的验收顺序

第一步，完成行为案例集，确认核心规则没有系统性违反。

第二步，让少量目标用户在真实、范围较小的任务中使用，记录难点和纠正，而不是立即追求大规模统计结论。

第三步，根据失败类型修改 Skill，再对未用于修改的新案例复验。

第四步，在相同案例和条件下比较不同宿主表现。不能因为 Skill 文本可复制，就宣称所有平台效果一致。

### 14.7 第一版试用条件建议

- 关键用途、立场和事实不存在未标明的编造。
- 用户的明确纠正得到执行，没有残留影响任务方向的旧要求。
- 澄清阶段不出现未经授权的外部动作。
- 已明确输入能够直接收敛，没有固定问卷式追问。
- “都不是”“不知道”和多选回答有可用处理路径。
- 最终说明可以区分已明确、暂定和需要补充的事项。

上述关键条件应逐案检查。体验指标的数值目标在首轮试用后再确定；发现关键失败应修复并复验，不以平均满意度覆盖。

## 16 产品风险与设计应对

### 16.1 选项诱导

AI 给出的选项可能缩小用户的想象范围。应避免无依据推荐，保持表达平衡，允许否定全部，并在用户给出新表达时离开原选项框架。

试用时关注用户是否只是选了最像答案的一项。可让用户在最后说明“哪部分是你原本就想要的，哪部分是看了建议后才决定的”，帮助区分意图识别与新增决策。

### 16.2 表面完整掩盖错误

流畅的任务说明可能隐藏未经确认的要求。最终检查要逐项追溯关键陈述的来源，尤其是用途、立场、事实、承诺和删除范围。

对暂定内容保留标签，即使影响文案简洁也不能省去重要区别。

### 16.3 过度澄清

固定框架容易让模型觉得字段必须齐全。停止条件应始终优先于框架完整度。已明确输入和简单修改应纳入常规回归案例。

### 16.4 把澄清扩展成方案设计

模型可能为了帮助用户而提出大量业务建议、技术架构或完整项目计划。只保留用于选择方向的必要差异，小样限制在能帮助判断的范围。

当用户进一步要求完整方案时，明确进入新的执行任务，并保留已经澄清的要求。

### 16.5 错误更新与上下文丢失

长对话中容易保留过时假设或漏掉早期边界。围绕重要变化维护简短任务状态；在输出前检查用途、重点、边界、暂定和未决事项。

第一版不依赖不可验证的跨会话记忆。必要交接以用户可阅读的任务说明为准。

### 16.6 为评价指标改变行为

只优化轮次会导致过早收敛，只优化确认率可能增加诱导。产品评估应同时检查忠实程度、负担、纠正与可用性，保留失败案例，不用单一指标替代判断。

## 17 第一版实施与迭代安排

### 17.1 阶段一 完成 Skill 行为规范

**交付物：**精简的 `SKILL.md`、必要的引导案例和验收案例集。

**完成条件：**另一位实现者只阅读这些文件，就能知道何时提问、如何生成选项、怎样处理否定、怎样收敛以及何时不应默认。

不把本产品方案全文复制进 `SKILL.md`。产品方案解释设计原因，Skill 只保留影响运行决策的规则和必要示例。

### 17.2 阶段二 完成场景验证

**交付物：**案例运行记录、实际任务说明和问题清单。

**完成条件：**核心案例得到行为检查；关键失败已修复并复验；没有只凭模型自己的摘要宣称通过。

用未参与修改的新案例检查泛化。针对失败修改对应规则，避免每个失败都增加一条绝对要求。

### 17.3 阶段三 小范围真实试用

**交付物：**用户回答困难记录、任务保真检查、改进建议。

**完成条件：**能够辨认用户在什么场景下需要帮助、哪类选择难以理解、什么情况下小样更有效，以及是否存在明显诱导。

试用反馈只保存完成产品验证所必需的内容，真实材料的收集与使用遵守已有授权，不自动积累成知识库。

### 17.4 阶段四 宿主适配

**交付物：**纯文字最低能力说明，以及经过实际验证的宿主适配说明。

**完成条件：**不同宿主都能保留自由纠正入口、确认粒度和暂定状态。涉及提问工具、文件访问及 Skill 加载方式时，依据实际可用能力处理。

### 17.5 第一版暂缓事项

- 大规模行业模板库。
- 独立网页和复杂需求管理界面。
- 跨会话画像、长期偏好学习及自动写入记忆。
- 需求评分仪表盘和未经校准的综合成功分数。
- 为澄清过程固定指定不同模型或多代理分工。
- 自动执行澄清结果和自动选择后续工具。

只有真实试用证明这些能力能解决当前机制无法处理的重复问题，才考虑扩展。

## 18 关键产品决策记录

| 决策 | 当前采用方式 | 设计原因 | 后续调整依据 |
| --- | --- | --- | --- |
| 用户入口 | 一句话、零散消息或现有材料 | 不要求先写完整需求 | 哪些输入无法形成有效澄清 |
| 通用性来源 | 固定判断机制，动态生成问题 | 避免行业问卷无限扩张 | 跨场景失败是否具有共同原因 |
| 主要交互 | 少量具体选择，允许自由纠正 | 减轻从零表达负担 | 用户是否理解选项差别 |
| 默认问题数量 | 一轮一个主要问题 | 便于判断并减少遗漏 | 独立简单问题能否合理合并 |
| 选项推荐 | 意图不明时不默认推荐 | 防止建议替代用户判断 | 是否存在清楚的条件依据 |
| 用户答不上来 | 切换经历、对比或短小样 | 利用辨认与纠正能力 | 哪种方式实际带来新信息 |
| 需求记录 | 来源与状态分开 | 防止材料、推测、确认混淆 | 纠正和交接中是否出现混用 |
| 停止方式 | 足够明确即收敛 | 不为字段完整性追问 | 过早结束与过度追问的案例 |
| 最终交付 | 自然语言任务说明 | 用户可核对，后续可使用 | 是否仍需大量重新解释 |
| 第一版架构 | Skill 规则与少量参考案例 | 先验证机制，降低实现负担 | 是否有明确、反复出现的能力缺口 |

## 附录 A 任务说明的组织约定

任务说明按必要程度包含以下内容。实际输出应自然连贯，不必总使用这些标签。

```text
需要完成的任务
  完成什么动作或形成什么结果

用途与重点
  给谁使用，希望帮助理解、判断或推动什么

输入范围
  使用哪些材料，哪些内容需要保留

重要边界
  不可改变的事实、立场、范围与权限

暂定安排
  用户明确愿意先试用的方向，或明示采用的低影响细节

未决事项
  仍需补充的关键问题，以及是否阻碍下一步
```

简单任务只输出前面一两项与必要边界。复杂任务可以展开全部适用项。任何事项没有依据时，不为了结构完整而编造。

## 附录 B 交互示例写作约定

**开始澄清：**“你提到……，我先按……理解。你更希望……还是……？”

**收到纠正：**“明白，你关注的是……。原来的……方向先撤掉。现在只需要确认……”

**用户不知道：**“不用先想清楚怎么做。就最近一次来说，最麻烦的是……还是……？”

**需要小样：**“我先给一个很短的结构，你看看哪部分接近，哪部分不对。”

**解释取舍：**“如果优先……，会保留……；如果优先……，则需要……。你更看重哪一项？”

**保留缺口：**“目前已明确……。还缺少……，它会影响……。其他细节可以后面再定。”

**形成说明：**“根据你刚才的选择，可以这样表达这项任务……”

这些表达用于说明语气与确认方式，不作为每轮必须套用的固定模板。避免反复使用“明白”“完全理解”等回应，却没有更新实际任务。

## 附录 C 单次澄清结果复核清单

- [ ] 最终用途和重点能够追溯到用户表达或明确选择。
- [ ] 已明确的重要要求没有遗漏，已撤销的要求没有残留。
- [ ] 材料记载没有被当作已核实事实或额外指令。
- [ ] AI 的暂定安排与用户要求保持区别。
- [ ] 未决事项具体，且说明是否阻碍下一步。
- [ ] 任务说明使用用户容易理解的语言。
- [ ] 用户否定、补充或多选的完整含义已经体现。
- [ ] 没有为了减少轮次而默认核心目标、立场或承诺。
- [ ] 没有为填满框架询问不影响当前做法的细节。
- [ ] 澄清阶段的例子没有演变成未经请求的完整执行。
- [ ] 后续 Agent 可以识别明确的下一步及必要边界。
- [ ] 结束状态与真实信息充分程度相符。

该清单用于开发和验收，不向小白用户逐项展示，也不要求用户承担复核责任。
